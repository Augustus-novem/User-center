# Benchmark: M11 Community V1 Evidence

## Environment

- Date: 2026-09-08.
- OS/arch: Windows / amd64.
- CPU: 12th Gen Intel(R) Core(TM) i5-12490F, Go benchmark `-12`.
- Benchmark harness commit: `de608e4`, DB isolation fix: `88e8b73`.
- Local dependencies: MySQL/Redis/Kafka/Elasticsearch already running through the existing development environment.
- Results are local learning evidence, not production capacity, QPS, P95 or P99 claims.

## 1. Note detail cache layers

Data: one isolated benchmark note with one image; 50 sequential operations per path. Redis/local hit paths are warm. Miss path deletes the Redis entry outside the measured interval, then measures Redis miss + MySQL load + cache fill.

Command:

```text
go test -tags=e2e ./internal/repository -run '^$' -bench '^BenchmarkNoteDetailLayers_e2e$' -benchtime=50x -count=1
```

Raw output:

```text
BenchmarkNoteDetailLayers_e2e/mysql_only-12                  50  89418546 ns/op  11174 B/op  145 allocs/op
BenchmarkNoteDetailLayers_e2e/redis_miss_then_mysql-12       50  88719230 ns/op  13428 B/op  211 allocs/op
BenchmarkNoteDetailLayers_e2e/redis_hit-12                   50    265606 ns/op   1202 B/op   23 allocs/op
BenchmarkNoteDetailLayers_e2e/local_hit-12                   50       104 ns/op     24 B/op    1 allocs/op
```

Interpretation: on this Docker-backed Windows setup, Redis and local hits avoid the dominant MySQL round-trip. The miss path intentionally costs roughly the same as MySQL plus cache work.

## 2. Pull / Push / Hybrid Feed

Data: deterministic in-memory service harness. Publish compares 100/1,000/10,000 follower scans; read returns Top20. This isolates algorithmic work and allocations, not network or database latency.

Command:

```text
go test ./internal/service -run '^$' -bench '^BenchmarkFeedStrategies$' -benchtime=50x -count=1
```

Raw output:

```text
BenchmarkFeedStrategies/publish_push_followers_100-12          50    1710 ns/op    1372 B/op    5 allocs/op
BenchmarkFeedStrategies/publish_pull_followers_100-12          50      98 ns/op     128 B/op    1 allocs/op
BenchmarkFeedStrategies/publish_push_followers_1000-12         50   30498 ns/op   14368 B/op   50 allocs/op
BenchmarkFeedStrategies/publish_pull_followers_1000-12         50      60 ns/op     136 B/op    2 allocs/op
BenchmarkFeedStrategies/publish_push_followers_10000-12        50  312910 ns/op  140836 B/op  501 allocs/op
BenchmarkFeedStrategies/publish_pull_followers_10000-12        50      82 ns/op     136 B/op    2 allocs/op
BenchmarkFeedStrategies/read_push_top20-12                     50    7980 ns/op   17280 B/op   25 allocs/op
BenchmarkFeedStrategies/read_pull_top20-12                     50    5138 ns/op   14448 B/op   18 allocs/op
BenchmarkFeedStrategies/read_hybrid_top20-12                   50    8122 ns/op   23400 B/op   30 allocs/op
```

Interpretation: the controlled harness demonstrates Push publish work grows with follower count, while Pull avoids fanout writes. It does not prove the configured threshold 1000 is globally optimal; real Redis/MySQL workloads and read/write ratios decide that.

## 3. Outbox → Kafka

Data: 20 sequential events, one-partition random topic, isolated random MySQL schema. Timed path includes Outbox insert, pending query, synchronous Kafka send with `WaitForAll`, Outbox mark and partition-consumer receive. Topic/schema are cleaned after the run.

Command:

```text
go test -tags=e2e . -run '^$' -bench '^BenchmarkOutboxKafkaLatency_e2e$' -benchtime=20x -count=1
```

Raw output:

```text
BenchmarkOutboxKafkaLatency_e2e-12  20  141627900 ns/op  49502 B/op  427 allocs/op
```

Before isolation, the same benchmark used the shared `user_center.event_outbox` while the application Relay was running and failed with `event outbox not found`: another Relay could publish/mark the selected row first. The isolated rerun passed and the failure is retained as evidence of the documented no-claim multi-Relay limitation.

## 4. Search ES / bounded DB fallback

Data: one note in an isolated random MySQL schema and one random ES index; 20 sequential warm queries. Both are cleaned after the run.

Command:

```text
go test -tags=e2e . -run '^$' -bench '^BenchmarkSearchPaths_e2e$' -benchtime=20x -count=1
```

Raw output after DB isolation:

```text
BenchmarkSearchPaths_e2e/elasticsearch_warm-12      20   6675595 ns/op  61601 B/op  173 allocs/op
BenchmarkSearchPaths_e2e/mysql_bounded_fallback-12  20  43830650 ns/op  18266 B/op  134 allocs/op
```

Interpretation: warm ES was faster for this exact one-document fixture. The fallback result only proves the bounded path operates; it is not an endorsement of `%keyword%` search at scale.
